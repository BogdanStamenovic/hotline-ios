**Everything else goes down with archserver:** hotlined, the Discord bridge, the

**This is fixable, and it is not a hardware limit.** I checked rather than
accepting the report:

```
enp4s0   Supports Wake-on: pumbg      <- 'g' is magic packet. The NIC can do it.
         Wake-on: d                   <- it is simply switched off
         Link detected: no            <- and there is no cable in it
phy2     WoWLAN is disabled           <- disabled, not unsupported
```

So "archserver cannot be woken remotely" is two settings and a cable, not a
capability the machine lacks. Plug ethernet into `enp4s0`, then:

```
sudo ethtool -s enp4s0 wol g
```

and make it survive reboots with a udev rule or `networkd`'s `WakeOnLan=magic`,
since `ethtool` alone does not persist. After that, `wakeonlan a8:a1:59:fd:4d:13`
from the laptop or your phone brings it up, and nights like this one end with
the box reachable instead of needing you in the room. Worth twenty minutes.

The wifi path is the less promising half — WoWLAN reports *disabled* rather than
unsupported, but the dongle failed with `-22` when it was actually exercised, so
I would put the cable in rather than chase the rtw89 driver.

## The thing I found while shutting down, which was worth the night

The daemon your phone talks to **was not a service.** It was a hand-launched
process with no unit. Powering this box off would have left you with a dead app
in the morning and no obvious way to bring it back.

Writing the unit exposed a worse bug underneath it. The daemon binds two
addresses: the tailnet IP your phone dials, and loopback for the hook. Given a
*list*, `asyncio.start_server` binds whatever it can and raises only if **every**
address fails — and loopback always succeeds. So at boot, before tailscaled is
up, the daemon bound loopback alone, **logged that it was listening on the
tailnet address anyway**, passed `/health`, answered every local curl, and was
unreachable from your phone. `Restart=always` could not have saved it, because
there was no failure to restart from.

That is the loopback-doorbell shape for the fifth time on this project, and this
time it was introduced *by* the fix for the previous one: appending loopback is
exactly what made "could not bind on any address" unreachable.

Both halves are fixed. The library now reports the sockets it actually has
rather than the list it was handed (`hotline@e3a6f58`), and the daemon exits
when the phone's address is missing so the restart policy can retry
(`hotline-ios@db03f5e`).

Measured, not assumed:

- Against an absent address the process exits 1, and systemd restarted it **8
  times in 20 seconds** without giving up.
- Against the real address it binds both and reports `sip+confirmed`.
- On the previous boot of this box a user unit came up **7 seconds** after boot
  with nobody logged in, so the linger mechanism works here.
- Tailscale takes **18 seconds** from boot to serving `100.72.2.62`. At
  `RestartSec=5` expect three or four failed starts in the journal at boot and
  then silence. **That is the design working, not a fault.**

So when you power archserver on, the app's server comes back by itself.

```
systemctl --user status hotline-ios
journalctl --user -u hotline-ios -f
```

The unit is in the repo at `deploy/hotline-ios.service`. It carries no secrets:
the daemon loads `.env` itself at startup.

## CI: the honest state

**No simulator has ever booted, and nothing has been filmed.** Repo is public
(`BogdanStamenovic/hotline-ios`), the workflow exists and reaches the build
step, and every run has failed there.

The blocker is real and worth your attention, because it says the device build
and the CI build disagree about the language rules:

```
FleetRow.swift:303     PinBar         conformance to 'Animatable' crosses into main actor-isolated code
MapLayer.swift:440     RouteTimeline  same
OverlayLayer.swift:255 GlyphRow       same
```

Every `ViewModifier` and `Shape` in the app that conforms to `Animatable` is
already marked `nonisolated`. Those three are the only `View: Animatable` types
and the only ones missing it — `animatableData` is a nonisolated requirement,
because SwiftUI reads it off the main actor while animating. So it is a source
defect, not a build-settings problem.

**What matters to you:** xtool's Swift 6.2 compiles all three without complaint,
which is why this never showed up in a device build. Xcode 26 rejects them. The
app on your phone is therefore doing something the newer compiler considers a
data race, in three animated views.

Cost is not a concern — Actions is free on public repos, macOS runners included.

**I fixed it (`0b00897`) but could not verify the fix.** `RouteTimeline` and
`GlyphRow` took `nonisolated` at the struct, matching the five that already had
it. `PinBar` could not — it holds `@State` and `@Environment`, and the compiler
rejects `nonisolated` on property wrappers — so it opens the hole exactly as
wide as the protocol needs: the stored property and `animatableData` itself,
with `body` and both wrappers left on the main actor. Established by compiling,
not by reasoning; the struct-level form was tried on all three first and the
compiler picked out `PinBar` specifically.

**It worked.** The runner confirmed it: the three `Animatable` errors are gone
and the app compiles for the simulator. That was the real blocker, and it is
down.

What the runner hit next was in the test harness rather than the app:

```
error: type 'XCTOSSignpostMetric' has no member 'scrollDecelerationHitches'
```

That member was invented. I removed it rather than guessing a replacement —
some near neighbour of the name probably exists, but choosing one without a Mac
to compile against is the same guess that produced the original, and each guess
costs a full macOS run to disprove. The stronger reason was already written in
the comment above it: signpost metrics only fire for `UIScrollView`-backed
surfaces, and the fleet list is absolutely-placed rows over a hand-rolled
`scroll` value — so the correct name would have bought a metric that measures
nothing, which is precisely the habit this CI work exists to break.
`XCTClockMetric` has no such precondition, so the drag is still measured, in
wall-clock rather than hitches. Fixed in `b42ca42`.
